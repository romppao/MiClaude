# Motivos técnicos y límites

Este índice conecta implementación y explicación. Las decisiones formales nuevas se registran con el [protocolo ADR/RFC](../decisiones/README.md); esta página no convierte recomendaciones en acuerdos ni inventa autores de decisiones pasadas. Las fuentes citadas permiten comprobar cada motivo.

| Elección vigente | Motivo y alternativa | Fuente y cuándo reconsiderarla |
|---|---|---|
| Monolito modular | El plan evita complejidad de microservicios mientras no exista necesidad medida. Se separan responsabilidades dentro del repositorio. | [PLAN](../PLAN.md), [prueba de arquitectura](../../tests/unit/arquitectura.test.ts). Reconsiderar ante límites medidos de operación/equipo; no afirmar capacidad por número de líneas. |

Una API REST separada sería otra superficie que mantener. Esta es una explicación de la implementación actual. | [layout](../../src/app/layout.tsx), [acciones](../../src/app/actions/), [arquitectura](../ARQUITECTURA.md). Una aplicación nativa con clientes independientes puede requerir un contrato API explícito. |
| Guardas en cada acción | Cualquier persona puede intentar una petición aunque no vea el botón. La pantalla ayuda a navegar; la acción autoriza. | [DESARROLLO](../DESARROLLO.md), [autorización](../../tests/unit/autorizacion.test.ts). Se conserva con cualquier cambio de interfaz. |

Mantener al cambiar proveedores de correo o acceso. El enlace de baja tiene su contrato propio. |

Comprobar visibilidad antes preserva privacidad. | [images](../../src/lib/profiles/images.ts), [ruta de imágenes](../../src/app/imagenes/%5Bkind%5D/%5Bid%5D/%5Bslot%5D/route.ts). ## Registrar una decisión nueva

Incluir problema concreto, alternativas (también conservar lo actual), evidencia reproducible, elección, consecuencias, archivos afectados, riesgos, criterio para revisar y quién la aprobó. Enlazar la decisión desde el contrato o guía afectada. No crear una ADR que declare aprobado un proveedor, cambio de política o capacidad que no se ha comprobado.

## Escalar con evidencia

La documentación facilita cambiar el sistema y evita perder conocimiento; no garantiza ausencia de fallos ni capacidad ilimitada. Para decidir una optimización: fijar escenario y presupuesto, medir consultas/latencia/errores/recursos, proponer cambio, repetir la medida y conservar datos y condiciones. Las tareas T-004 a T-010 del [plan](../PLAN.md) cubren varias mejoras; no presentarlas como desplegadas por figurar en una lista.
