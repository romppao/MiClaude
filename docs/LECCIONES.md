# Lecciones aprendidas y cómo retomar

Errores, callejones sin salida y sus causas reales, para no repetirlos y para poder retomar cualquier punto.
Se completa en cada sesión (ver [`DIARIO.md`](DIARIO.md)). Formato: **qué pasó → causa real → cómo se resolvió → qué hacer la próxima vez**.

## Producto y decisiones

| Qué pasó | Causa real | Cómo se resolvió / regla |
|---|---|---|
| El primer MVP copiaba el enfoque BoxRec (profesional, catálogo) | Se interpretó la petición literalmente y no se había explorado el foco real del fundador | El fundador reorientó a amateur + valoración del público + Madrid. **Regla:** enseñar algo pronto y reorientar es más barato que planificar en abstracto |
| Se asumió que registrar «tu propio récord» era suficiente | Un dato autodeclarado no es fiable | Niveles de respaldo (`SELF_REPORTED` → `CONFIRMED` → `VERIFIED`, `DISPUTED`). **Regla:** todo dato que aporta un usuario necesita un estado de fiabilidad visible |
| El diseño gráfico no se trató | El fundador prefirió aplazarlo (los diseños generados no le suelen gustar) | UI provisional y funcional. **Regla:** no invertir en diseño hasta que lo pida; si se aborda, consultar antes qué le gusta |

## Técnicas

| Qué pasó | Causa real | Cómo se resolvió / regla |
|---|---|---|
| El build de Next.js fallaba con «Can't resolve '@/lib/db'» | Se instaló **TypeScript 7**, incompatible con Next 15 (no ofrece la API que Next necesita, y por eso no leía los alias del `tsconfig`). El mensaje de error real solo salió después | Se fijó TypeScript 5 y se usan imports relativos. **Regla:** ante un error de resolución de módulos, mirar antes las versiones de las dependencias que la configuración. Fijar versiones mayores de TypeScript |
| Un test e2e marcaba «OK» sin comprobar nada | Escribí `check(..., true)` como marcador y se me pasó | Se sustituyó por una comprobación real (y para eso hubo que ocultar el formulario de valorar a quien no tiene email verificado: era un fallo de producto, no solo de test). **Regla:** un test que no puede fallar no es un test; revisar los marcadores antes de dar algo por probado |
| El script e2e fallaba en el primer `click("button")` | Con la sesión iniciada, el primer botón de la página era «Salir» de la cabecera | Selectores acotados a `main form button`. **Regla:** selectores específicos en tests de navegador |
| Se probó contra el servidor **antiguo** y `/registro` daba 404 | Una prueba anterior dejó `next start` vivo en el puerto; el nuevo no arrancó (`EADDRINUSE`) | Matar el proceso y relanzar. **Regla:** comprobar el log de arranque y que el puerto es del build actual antes de diagnosticar |
| `pkill -f "next start"` mataba también mi propia shell | El patrón coincidía con la línea de comandos del propio comando | Patrón con corchetes (`next-serve[r]`) o proceso por PID. **Regla:** no usar `pkill -f` con un texto que aparezca en el propio comando |
| Redirect abierto en la acción de valorar | El destino `back` venía del formulario sin validar | Se limita a rutas internas (`/…` y no `//…`). Detectado al revisar el código antes de probar. **Regla:** nunca redirigir a una URL que venga del cliente sin validarla |
| Un cambio en el esquema pedía `--accept-data-loss` | Prisma avisó por la restricción única nueva en `Boxer.userId` | Aceptado solo porque era la BD local de demostración. **Regla:** con datos reales, migraciones (`prisma migrate`), no `db push` |
| El PostgreSQL local se paraba entre sesiones | El entorno de trabajo es efímero y no conserva los procesos | Reiniciarlo con `pg_ctl` antes de probar. **Regla:** si «no puede alcanzar la base de datos», comprobarlo antes de sospechar del código |
| El CI no se ejecutaba al subir la rama (resuelto: los 3 primeros runs en éxito) | El workflow solo se disparaba en `push` a `master/main` y en pull requests; la rama no tenía PR | `on: push` sin filtro de ramas. **Regla:** comprobar en GitHub que la primera ejecución arranca de verdad |
| El registro de auditoría de reclamaciones decía «aprobada» aunque la aprobación podía rechazarse por las condiciones | Se escribió el `audit` antes de pensar en las ramas de decisión | Se calcula el resultado real (`approved`) y se registra junto con lo que se pidió. Detectado al releer. **Regla:** un registro de auditoría refleja lo ocurrido, no lo intentado |
| Un cambio de texto con `replace` no se aplicó y no dio error | El patrón no coincidía con el formato (Prisma reformatea el esquema); el fallo solo apareció después en tipos | Editar con la herramienta de edición o verificar con `grep` tras cada sustitución. **Regla:** comprobar que un reemplazo automático se aplicó |

| Un test contaba «todos los `role=alert`» y daba 2 | Next.js añade su propio elemento con ese rol | Se acota el selector al texto del mensaje. **Regla:** en tests de navegador, seleccionar por contenido o clase propia, no por roles genéricos que el framework también usa |
| El CI de GitHub falló en dos envíos seguidos (runs 4 y 5) sin que me diera cuenta hasta después | En local el test pasaba «a veces»; la carrera de sincronización del sello de gimnasio se manifestó en el CI, más lento. Yo no consulté el CI de esos envíos | Se corrigió con una espera determinista (`1faa28d`) y los runs siguientes pasan. **Regla:** tras cada push, mirar el resultado del CI antes de dar el trabajo por bueno; un test que pasa una vez en local no demuestra que no sea intermitente |
| El test del sello de gimnasio falló de forma intermitente | Se esperaba con `networkidle`, que puede volver antes de que termine la acción del servidor | Se espera a un estado visible («Retirar sello»). **Regla:** esperar al resultado en pantalla, no al tráfico de red |
| Al cambiar textos de botones a lenguaje llano, el e2e dejó de encontrarlos | Las pruebas buscan por texto | Se actualizaron las pruebas. **Regla:** al cambiar un texto, buscar dónde lo usan las pruebas |
| Varias acciones fallaban sin decir nada (p. ej. valorar un combate no permitido) | Se redirigía a la misma página sin mensaje | Todas devuelven un aviso o un problema claro. **Regla:** ningún fallo silencioso; toda acción responde |

| Prisma se negó a hacer `db push --force-reset` | Prisma detecta que lo lanza una IA y exige el consentimiento explícito del usuario, porque destruye todos los datos | **No se forzó.** Se creó una base de datos nueva y vacía y se aplicó el esquema ahí, sin destruir nada. **Regla:** ante una protección destructiva, no rodearla con otro comando equivalente; buscar una vía que no destruya datos o pedir permiso |
| Un script de edición falló con `missing 1 required positional argument` | La función auxiliar exigía una etiqueta que no pasé | Como el fichero solo se escribe al final, no quedaron cambios a medias. **Regla:** scripts de edición todo-o-nada, con aserciones que fallen si un patrón no existe |
| Una comprobación e2e falló de forma intermitente tras acciones que cambian un contador | Se leía el contador antes de que la página terminara de actualizarse | Se **midió** el retraso (entre 4 y 30 ms tras el aviso) y se espera de forma explícita. **Regla:** medir antes de asignar una causa; y esperar al estado visible, no leerlo de inmediato |

| No se pudo abrir ni raunder.es ni boxrec.com para analizar a la competencia | La política de red del entorno bloquea esos dominios (también Wikipedia) y las búsquedas no devuelven nada de Raunder | **No se rodeó el bloqueo ni se rellenó con suposiciones.** El análisis separa lo comprobado, lo general sin comprobar y lo no analizado, y se pide habilitar los dominios. **Regla:** si falta la fuente, decirlo; un análisis que parece completo pero no lo es engaña al fundador |
| Al pedir «todo en español» aún salían pantallas en inglés | Las páginas de «no encontrada» y de error que genera Next.js por defecto están en inglés y no las habíamos creado | Se añadieron `not-found`, `error` y `global-error` en español. **Regla:** revisar también lo que el framework muestra por su cuenta |

| El CI falló en el run 17 en «el récord de partida detallado se muestra como declarado» y el run 18, con el mismo código, pasó | La comprobación leía el texto de la página justo después de aparecer el aviso; en el CI, más lento, el contenido aún no se había actualizado. Había más puntos iguales: aprobaciones del moderador que seguían con `networkidle` sin esperar a que la acción terminara | Todas las esperas tras una acción pasan a esperar a un estado visible concreto (`seen(...)`, notificación o desaparición de un botón); ya no queda ningún `networkidle`. **Regla:** en una prueba, nunca se lee el contenido justo después de una acción; y, cuando algo falla en el CI y no en local, se **busca la misma raíz en todo el fichero**, no solo en la línea que falló |
| Dos ejecuciones del e2e a la vez fallaban | El nombre de la organización era el mismo en todas las ejecuciones y el moderador veía varias solicitudes idénticas | Nombre único por ejecución. **Regla:** todo dato que el test crea y luego busca por texto debe llevar un identificador único; probar en paralelo destapa estos fallos |

## De la corrección de la auditoría (30 de septiembre de 2026)

| Qué pasó | Causa real | Cómo se resolvió / regla |
|---|---|---|
| La búsqueda sin tildes no encontraba «Núñez» ni «Búsqueda» (la «ñ» daba «u» y la «ú» daba «o») | La tabla de letras de `translate()` de PostgreSQL emparejaba por posición y una de las dos cadenas tenía una «o» de más: quedó desalineada | La tabla se construye **por pares** (`lib/common/search.ts`) y una prueba unitaria comprueba que cada letra coincide con la normalización de JavaScript. **Regla:** dos listas que deben ir alineadas se generan de una sola fuente; las pruebas de navegador lo cazaron, no la lectura del código |
| El CI falló (ejecución 25) en «los listados largos se paginan» y en local pasaba | La prueba necesitaba más de 24 peleadores y mi base local tenía cientos; en el CI la base empieza vacía | La prueba prepara sus propios datos con SQL. **Regla:** una prueba no puede depender del volumen de datos que hay en la base; y **probar sobre una base vacía** (clon limpio) antes de dar por bueno un cambio de pruebas |
| Tres pruebas dieron falsos fallos tras añadir la paginación y el mensaje «no hemos encontrado nada para …» | Los listados están paginados y acotados por nombre; la página de búsqueda repite el texto buscado, así que «la página no contiene X» dejó de servir | Las pruebas acotan por nombre y comprueban la **ausencia del enlace**, no del texto. **Regla:** si la pantalla repite lo que se busca, no se puede probar una ausencia con `includes` sobre el texto |
| Tras reiniciar el servidor, las pruebas seguían viendo el código antiguo (otra vez) | El reinicio mataba el envoltorio `npx`, no el proceso `next-server`, que seguía ocupando el puerto; el nuevo arranque fallaba con `EADDRINUSE` | Se mata **por puerto** (no por nombre) y el script de reinicio falla si el log contiene `EADDRINUSE`. **Regla:** tras arrancar, mirar el log; nunca fiarse de «responde 200» (puede responder el servidor viejo) |
| `pkill -f` mató mi propio intérprete de comandos (otra vez) | El patrón aparecía en la línea de comandos del propio comando (`next start`) | No usar `pkill -f` con texto que esté en tu propia orden; matar por PID o por puerto |
| El servidor y PostgreSQL desaparecieron entre dos comandos | El contenedor de trabajo estuvo parado un tiempo (hora del log: horas después) y no conserva procesos | Reiniciar PostgreSQL antes de probar (`pg_ctl`). **Regla:** ante `ERR_CONNECTION_REFUSED` o «no puede alcanzar la base de datos», comprobar primero que los procesos siguen vivos |
| Una prueba que lee un contador o un enlace justo después de ver el mensaje de aviso falló (dos veces) | El aviso aparece antes de que termine de pintarse el resto de la página nueva | Siempre `seen(locator)` (espera) y nunca `count()` inmediato. Ya estaba en las lecciones; se repitió porque escribí la prueba deprisa |
| Un campo con `minlength` impedía probar la validación del servidor | El navegador bloquea el envío antes de llegar al servidor | En la prueba se quita el atributo para comprobar la regla del servidor (`removeAttribute`). **Regla:** las reglas se prueban en el servidor, que es lo que no se puede saltar |
| La verificación adversarial de los hallazgos 91–99 y la pasada de «huecos» **no se completaron** (y en el traslado dije por error que eran del 53 al 99, sin tres refutaciones) | Un flujo con 308 agentes y ~20 millones de tokens agotó el límite de uso de la sesión; y escribí el estado de la auditoría a partir de una copia de los datos anterior al final del proceso | Se reanudó el flujo con el mismo identificador (solo repite lo que falló; el límite de uso volvió a cortarlo, ahora en 3 hallazgos y en los «huecos») y `AUDITORIA.md` se genera desde el **resultado final**. **Regla:** un flujo larguísimo debe volcar los resultados parciales a disco según llegan y dividirse en fases; y antes de afirmar qué está verificado, leer el resultado final, no una copia intermedia |
| `cache()` de React en `getUser` habría dejado la sesión obsoleta | Con acciones que cierran la sesión y redirigen, la página de destino se pinta en la misma petición y reutilizaría el usuario anterior | No se usa; se acepta la doble consulta. **Regla:** no memorizar por petición nada que una acción pueda cambiar antes de redirigir |
| Los documentos (README, ARQUITECTURA) seguían describiendo el modelo antiguo («Boxer», «Rating») | Dejé la documentación de los bloques 1 a 5 para el final en lugar de hacerla **al terminar cada bloque**, como pidió el fundador | Se reescribieron en el traslado. **Regla:** la documentación se hace al cerrar cada bloque, no «al final»; el fundador lo pidió expresamente |
| El texto de privacidad y los plazos de conservación los escribí yo | La auditoría pedía definirlos y no había criterio del fundador | Se marcan como **propuesta pendiente de revisión jurídica** (`TRASLADO.md`, `IDEAS.md`). **Regla:** lo que tiene consecuencias legales lo propone la IA pero lo valida una persona |
| El proceso de prueba del primer CI tras el cambio de configuración avisó de `APP_URL` | En producción el servidor ya no arranca sin `APP_URL` (a propósito) | El CI y `.env` la definen. **Regla:** toda variable obligatoria nueva se añade a `.env.example`, al CI y al README en el mismo commit |
| Una comprobación de «la página no falla» no podía fallar | Buscaba la frase «Algo ha salido mal»; la aplicación dice «Algo no ha salido como esperábamos». Ocultó que `?problema=__proto__` rompía la página | Se corrigió la frase y el error (`lookup` en el aviso). **Regla:** toda aserción negativa se prueba primero contra el código roto para ver que **falla**; y los textos que se buscan se copian de la aplicación, no de memoria |
| «No perder lo escrito» no funcionaba: los campos se rellenaban y volvían a vaciarse | React 19 reinicia (`reset`) los campos no controlados de un formulario cuando termina su acción | Se escucha el evento `reset` y se rellena justo después, sin pisar lo que la persona ya haya vuelto a escribir. **Regla:** al tocar formularios de acción, probar en un navegador real el momento *posterior* a la acción |
| La prueba de «sin marcar la casilla de confirmación» eliminó la cuenta de verdad | La casilla de confirmación se restauró marcada tras un error de contraseña | Las casillas no se recuerdan nunca. **Regla:** una confirmación de algo irreversible hay que darla de nuevo cada vez |
| Un código de mensaje de las acciones (`cartel_boxeadores`) no tenía texto: la persona no veía nada | Se escribió el código en la acción y no en `messages.ts`; nada lo comprobaba | Prueba unitaria que lee `actions.ts` y exige texto para cada código. **Regla:** lo que se puede comprobar leyendo el código, se comprueba con una prueba |
| `required` y `minlength` del navegador impedían probar las reglas del servidor | El navegador bloquea el envío antes de llegar al servidor | En la prueba se quita el atributo; la regla que importa es la del servidor. **Regla:** no quitar el atributo en la aplicación para facilitar la prueba |
| Hallazgos «refutados» que en realidad ya estaban corregidos | La verificación se hizo sobre el código de después de corregirlos | Se anota en `AUDITORIA.md`. **Regla:** al interpretar «refutado», comprobar *cuándo* se verificó respecto a las correcciones |
| Ver el resultado de un comando con `head` dio `EPIPE` | `head` cierra la tubería antes de que el script termine de escribir | Inofensivo; no es un fallo de la aplicación. **Regla:** no tuberear a `head` un script que sigue escribiendo si el resultado importa |

## De las pruebas por personas y la revisión de código (1 de octubre de 2026)

| Qué pasó | Causa real | Cómo se resolvió / regla |
|---|---|---|
| Una dirección con `?constructor=y` daba error 500 en siete pantallas (y `?q=%00` o un parámetro repetido en otras) | Next.js entrega `searchParams` como una promesa a la que añade cada parámetro como propiedad propia: un parámetro llamado «constructor» sustituye el de la promesa y `await` falla; un carácter nulo hace fallar a PostgreSQL; un parámetro repetido llega como lista | `src/middleware.ts` limpia la dirección antes de que llegue a ninguna pantalla (un solo sitio) y `str()` limpia los campos de formulario. **Regla:** la entrada del usuario se sanea en un único punto y se prueba con nombres y valores hostiles en **todas** las pantallas con filtros |
| Una regresión de CSS mía (`align-items:flex-end` en `form.search`) dejó nueve formularios torcidos y estrechos y ninguna prueba lo detectó | Lo añadí al corregir otra cosa; axe no mide la apariencia y las pruebas de navegador buscan elementos, no su aspecto | `alignItems: stretch` en los formularios en columna. **Regla:** tras tocar CSS global, **mirar capturas** de las pantallas clave (formularios, tablas, móvil); un formulario torcido no lo ve ningún análisis automático |
| La prueba de «ninguna pantalla se sale del ancho en el móvil» pasaba y la ficha de una velada se salía (584 px en 360) | La lista de pantallas medidas no incluía las fichas con datos (en el CI la base está vacía y no hay fichas que abrir) | La prueba crea su propio peleador y combate y mide su ficha y su velada. **Regla:** una prueba de pantallas debe **crear los datos que hacen que la pantalla sea interesante**, no medir solo las vacías |
| Dar clic en un resumen para abrir un formulario tras un error lo cerraba (la prueba lo hacía y pasaba) | La prueba asumía el comportamiento antiguo (el desplegable volvía cerrado y la persona no sabía dónde corregir) | Tras un error se abre solo el desplegable que contiene el formulario y se restaura lo escrito; la prueba comprueba que ya está abierto. **Regla:** si una prueba hace un gesto «para llegar al estado», comprueba antes que el estado no se alcanza solo |
| «No perder lo escrito» fallaba cuando el mismo error se repetía | La restauración dependía de que cambiase la dirección (`useSearchParams`); con el mismo error la dirección es idéntica y el efecto no se vuelve a ejecutar | También se escucha el evento `reset` (React vacía el formulario al terminar la acción) durante unos segundos tras enviarlo, y el formulario se identifica por los nombres de sus campos y no por su posición. **Regla:** no deduzcas «ha terminado la acción» de un cambio de dirección |
| Se podían probar cientos de contraseñas con peticiones simultáneas | El acceso comprobaba el límite, luego calculaba el hash (100–200 ms) y solo anotaba el fallo al terminar: todas las peticiones veían «0 intentos» | `reservar()` anota el intento **antes** de calcular el hash y lo devuelve si la contraseña era correcta. **Regla:** el límite de intentos se reserva antes de la operación costosa o secreta (anotar primero, contar después) |
| `resetPassword` calculaba un hash de 64 MiB antes de saber si el enlace servía | La acción es pública y el orden de las comprobaciones puso lo caro primero | Primero límite de frecuencia y comprobación barata del enlace; el hash después. **Regla:** en una acción pública, lo barato y lo que rechaza va primero |
| La confirmación del rival no estaba ligada al resultado que vio, y un combate confirmado sin resultado quedaba atascado | Se modeló la confirmación como «sí/no» sobre el combate, no sobre unos datos concretos | Huella del resultado (`boutVersion`) en el formulario y escritura condicionada al estado leído; si solo se confirmó el emparejamiento, añadir el resultado devuelve el combate a «pendiente de confirmar». **Regla:** quien confirma algo confirma **lo que vio**: el formulario lleva su versión y la escritura la comprueba |
| Dos moderadores podían pisarse (uno aprobaba y el otro dejaba «rechazada» una solicitud ya aprobada) | Las decisiones leían el estado fuera de la transacción y escribían con `update` sin condición | `updateMany` con el estado esperado y, si no encuentra nada, se descarta la decisión con un aviso. **Regla:** toda decisión de moderación se escribe condicionada al estado que vio quien decide |
| Al eliminar la cuenta quedaban nombres reales en el historial de cambios | El historial guardaba «antes» y «después» con datos personales y el borrado solo tocaba la cuenta y la ficha | Se vacían esos datos del historial (queda qué pasó y cuándo). **Regla:** al diseñar el borrado de datos personales, buscar **todas** las tablas que los copian (historial, avisos, correos) |
| Tras volcar la copia reorganizada al repositorio real, `tsc` falló con un módulo que no existía | `rsync` no estaba instalado y copié carpetas a mano: me dejé `prisma/seed.ts`, que el script de reorganización sí había reescrito | `diff -rq` entre la copia y el repositorio antes de validar. **Regla:** al trasladar un árbol, **compara los árboles**, no confíes en la lista de lo que crees haber copiado |
| Los dos flujos de agentes (revisión y 10 personas de prueba) se cortaron por el límite de uso de la sesión: solo terminó 1 persona de 10 y 3 revisores de 6, y ninguna verificación adversarial | Lancé 94 + 11 agentes de golpe, con ~20 minutos de trabajo cada fase, sobre una cuota compartida | Reproduje y corregí a mano cada hallazgo disponible (ver `docs/pruebas/hallazgos-2026-10-01.md`). **Regla:** los flujos grandes se lanzan **por fases** y con resultados parciales guardados (el diario del flujo permite reanudar); los hallazgos sin verificación adversarial se reproducen antes de corregirse |
| El servidor local y PostgreSQL desaparecieron otra vez al reiniciarse el entorno | El proceso de trabajo se reinicia y mata los procesos hijos | `pg_ctl start` y `scripts/entorno-aislado.sh iniciar`. **Regla:** al retomar, comprueba `pg_isready` antes de culpar a la aplicación |
| Di por corregido «no perder lo escrito si el mismo error se repite» y no lo estaba: el correo seguía desapareciendo a los 600 ms | Mi primera corrección escuchaba el evento `reset` de React, pero tras él Next.js vuelve a montar el formulario con la respuesta del servidor y lo vacía otra vez; mi prueba comprobaba otra cosa (que la contraseña se vaciara), que en el registro no ocurre | Se vigila también el DOM durante 8 segundos tras enviar (`MutationObserver`) y la prueba reproduce el caso real (dos accesos erróneos seguidos). **Regla:** una corrección de un fallo temporal se comprueba **mirando el estado a lo largo del tiempo** en el navegador (100 ms, 600 ms, 3 s), no solo al principio o al final |
| Una espera de la prueba (`waitForFunction`) fallaba a ratos con «Cannot read properties of null» | Mientras la página cambia, el campo no existe un instante y la función de espera lanza una excepción, que hace fallar la espera en lugar de reintentar | Las funciones de espera usan `?.` en todo lo que lean. **Regla:** el código que se ejecuta dentro de `waitForFunction` debe tolerar que el elemento aún no exista |
| Mis pruebas de navegador fallaban de forma intermitente al registrar combates seguidos | Esperaba el aviso «Combate registrado», que seguía en pantalla del envío anterior, y rellenaba el formulario justo antes de que React lo vaciara al terminar la acción | **Regla:** tras una acción, esperar a lo que cambia de verdad (la fila nueva), no a un aviso que puede ser el anterior; y comprobar el recuento solo después de ver la fila |
| El doble clic seguía enviando dos veces aunque desactivaba el botón | Desactivar el botón con `setTimeout(0)` llega tarde: el segundo clic ya había entrado | **Regla:** la protección de doble envío descarta el segundo `submit` de inmediato (`stopImmediatePropagation`) y solo después desactiva los botones para que se vea |
| Una prueba con `text=El cartel está vacío` fallaba con el cartel vacío | `text=` busca de forma parcial y sin distinguir mayúsculas: coincidía con una ayuda que decía casi lo mismo y Playwright exige un único resultado | **Regla:** localizar por rol y texto más específico (`p` con el texto completo) |
